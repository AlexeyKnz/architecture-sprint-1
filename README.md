1.2 Разделение на домены (DDD-подход)
На основе Domain-Driven Design выделены следующие бизнес-домены:

1.2.1 Аутентификация (authentication)
* Функционал:
    Регистрация и авторизация пользователей.

* Обоснование:
    В текущей реализации объединение логина и регистрации оправдано простотой системы.

    Потенциальное масштабирование: В высоконагруженных системах рекомендуется разделять эти сервисы для изоляции пиковых нагрузок (например, чтобы всплеск авторизаций не влиял на регистрацию) или при использование более сложной логики при аутентификации (2-ух, 3-ех факторной).

1.2.2 Профиль пользователя (userprofile)
* Функционал:
    Управление персональными данными пользователя.
    Редактирование профиля.

1.2.3 Карточки мест (cards)
* Функционал:
    CRUD-операции с локациями.
    Лайки.
    Отображение списка мест.

1.2.4 Общие модули (shared)
* Назначение:
    Реализация межсервисного взаимодействия, в моем случае event-bus(customEvents).
    Использование контекст пользователя в разных микрофронтендах (user-context).

1.2.5 Хост-приложение (host)
* Роль:
    Интеграция всех микрофронтендов в единый интерфейс.
    Управление роутингом и состоянием приложения.

1.3 Была выброна реализация микрофронтендов через Runtime-интеграцию с Webpack Module Federation.
* Причины :
    1.3.1 Независимость сборки и деплоя
        Каждый микрофронтенд собирается и деплоится отдельно
        Изменения в одном модуле не требуют пересборки всего приложения.
        Горячее обновление (Hot Deployment)
        Можно обновлять отдельные модули на проде без перезапуска основного приложения.
    1.3.2 Ленивая загрузка (Lazy Loading)
        Код загружается только при обращении к нему
        Например, если пользователь зашел на /UserAuth, подгрузится только UserAuth.
        Оптимизация скорости загрузки
        Не тащим весь бандл при старте приложения.
    1.3.3 Совместимость версий
        Разные микрофронтенды могут использовать разные версии библиотек
    1.3.4 Гибкость интеграции
        Динамическое подключение модулей
        Общие зависимости (Возможность шарить библиотеки между микрофронтендами )
    1.3.5 Снижение сложности разработки
        Можно разрабатывать микрофронтенд изолированно, а потом интегрировать его в хост.
    1.3.6  Масштабируемость
        Добавление новых модулей без переписывания кода
        Можно постепенно мигрировать с монолита, подключая новые модули рядом со старыми.
    1.3.7 Изоляция ошибок
        Падение одного модуля не ломает весь фронтенд

Также хотелось получше познакомиться с возможностями Webpack Module Federation, ранее опыта работы с ним не было.

1.4 Настройка межмодульного взаимодействия CustomEvents (Pub/Sub).

* Причины :
    1.4.1 Декомпозиция модулей:
        (Компоненты общаются через события, а не прямые вызовы — нет жестких зависимостей.)
    1.4.2 Простота интеграции:
        Работает даже между разными технологиями.
        Не обязательно использовать сложные инструменты.
    1.4.3 Асинхронность и масштабируемость :
        Отправителям не нужно ждать обработки
        Легко добавить новых подписчиков
    1.4.4 Гибкость payload:
        Передача различные объекты (массивы, строки и тд)
    1.4.5 Отказоустойчивость
        Подписчики не ломают отправителя.
